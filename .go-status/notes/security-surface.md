## Summary

**Root-owned platform processes:** None currently running as a persistent daemon on either host at scan time.
- Controller: 4 systemd units are *configured* `User=root` — `engineering-backup.service` (oneshot, fires via `engineering-backup.timer` every 30 min — next in a live wait), `engineering-github-policy-expiry.service` (state=**failed**, stale since 2026-09-07), `engineering-github-policy-reconciler.service` (inactive/dead), `engineering-gateway-credentials.service` (active/exited, oneshot). None had a live PID when checked, but the backup timer *will* spawn a root process again shortly — flag as a standing rule-2-relevant config item, not an active violation right now. All application engines (api, dashboard, scheduler, temporal-worker, notifier, migrate, evidence-ingest, acceptance-worker) run as the unprivileged `engineering-control` user; `hermes-gateway.service` runs as `hermes-gateway`; `engineering-github-worker.service` runs as `hermes`.
- Worker: no engineering-control/hermes process runs as root. Four `gpg-agent --homedir ...` daemons run persistently as root for the backup/mirror subsystem (`/etc/engineering-backup/gnupg`, `/var/lib/engineering-backup-mirror/{recovery,signing,verify}-gnupg`) — persistent root daemons tied to backup encryption, worth noting under rule 2 even though they're not LLM-related.

**Secret file permissions:** No world-readable secret files found. `~/.hermes/.env`, `~/.hermes/auth.json`, `~/.claude/.credentials.json`, `~/.codex/auth.json` are all `0600` owner-only on the controller; worker's `~/.hermes/project-adapters/*/adapter.env`, `~/.hmw/projects.d/*.env`, `~/.hmw/secrets/audit.env` are all `0600`. `/etc/engineering-control/env/` and `/var/lib/hermes-change-control/` are root-only (permission denied to `hermes`, could not be read without sudo — correct least-privilege posture, but contents unverified).

**Sudo status:**
- Controller: `sudo -n true` → `sudo: interactive authentication is required` (exit 1). **Not passwordless.** Did not attempt interactive auth.
- Worker: identical result. **Not passwordless.**

**Bottom line on the #1 rule:**
- **engineering-control** (this platform's own Temporal/CLI codebase, both the repo and every deployed `/opt/engineering-control/releases/*` snapshot on both hosts) is clean: no `openai`/`anthropic` SDK imports, no direct HTTP calls to LLM APIs, and its `subscription_only_environment()` helper actively strips `OPENAI_API_KEY`/`ANTHROPIC_API_KEY`/`*_BASE_URL`/etc. from every `codex`/`claude` CLI subprocess it spawns.
- The prior audit's **F-05** claim (`OPENAI_API_KEY` live in `~/.hermes/.env`) is **no longer true** — the variable is absent from `.env` (file mtime 2026-09-04, after the 2026-09-01 audit), and the matching `openai-api` entry in `auth.json` is now an orphaned/unbacked credential-pool record.
- The prior audit's **F-04/C1** claim (Hermes's own loop uses the `openai-codex` **HTTP** provider, hitting `chatgpt.com/backend-api/codex` with a spoofed `codex_cli_rs` User-Agent/originator instead of shelling out to the real `codex` binary) is **still true today**, confirmed against the exact release (`fecf78726c170f1f5fdadec7156c52ea3de4651b`) backing the currently-running `hermes-gateway.service` process. This remains the one live, real rule-1 violation. A remediation script/tests for it (`scripts/prepare-hermes-c01-cutover.py`) already exist in the repo but have not been applied.
