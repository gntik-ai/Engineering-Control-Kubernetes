## IMPORTANT ARCHITECTURE NOTE discovered during this pass

There are **two distinct Hermes/provider surfaces** on this host and the prior audit doc appears to
conflate them:

1. **Interactive/operator Hermes agent** — runs as uid 1000 (`hermes`), home `/home/hermes/.hermes`,
   used for manual CLI sessions (the `tmux` "codex" session and ad-hoc `claude`/`hermes` invocations
   seen in the live process list). This is what the 2026-09-01 audit doc almost certainly inspected.
2. **Production Hermes gateway** — systemd system service `hermes-gateway.service`, running as an
   **isolated, unprivileged service user `hermes-gateway` (uid 972)**, home `/var/lib/hermes-gateway/home`,
   secrets loaded via systemd `LoadCredential=` from root-owned files under `/etc/engineering-control/env/`.
   This is the identity that would actually receive Temporal-triggered work. Its config/secrets are
   **not readable by uid 1000** (by design — `drwx------ hermes-gateway:hermes-gateway`), and could not
   be verified in this session (see row below). This isolation is itself evidence the Sept-1 finding
   about weak secret handling was at least partially acted on.
3. Separately, the **`engineering-control`** Temporal-workflow layer (a different codebase at
   `/opt/engineering-control`, running as system user `engineering-control`) is what actually drives
   "missions" (audits, backlog work, issue delivery) via Temporal workers, and has its own live
   provider-health telemetry that is CLI-based (see row 1 below) — separate again from either Hermes
   agent config above.

## Summary of what could NOT be verified, and exactly why

- **Production gateway's own `config.yaml`/`.env`/logs** (`/var/lib/hermes-gateway/home/*`, and the
  credential source `/etc/engineering-control/env/gateway-platform.env`): all root/`hermes-gateway`-owned,
  `0600`/`0700`. `sudo -n true` / `sudo -n -l` both returned "interactive authentication is required" —
  no password was available non-interactively, and per the task's own constraint ("no sudo" / "use only
  if strictly necessary") I did not attempt to obtain one. This is the single biggest verification gap:
  it means I could **not** directly read the provider config of the exact process identity that Temporal
  would hand work to.
- **journalctl for `hermes-gateway.service` after its uid-972 migration**: journald's default per-UID
  read ACL means uid 1000 can only see log entries originally emitted by uid 1000 processes; entries from
  the current uid-972 process are invisible without `systemd-journal` group membership or root, neither
  available.
- **`/etc/engineering-control/policy`** (GitHub write-policy value) and **`/etc/engineering-control/env/control.env`**
  (engineering-api/dashboard secrets): both permission-denied to uid 1000 (owned by `root`/group
  `engineering-control`, which `hermes` is not a member of).
- **Raw network-connection inspection of the gateway process** (`ss -tnp`, `/proc/<pid>/fd`): permission
  denied (process runs as a different uid); could not directly observe outbound sockets to confirm/deny
  live HTTP calls from the gateway process itself in real time. Used the `engineering-ctl connections`
  health telemetry as the best available live substitute.
